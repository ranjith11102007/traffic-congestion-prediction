# Machine-learning module

Independent, framework-free pipeline for the traffic congestion model. It never
imports `backend/app`, so it can run on a machine with no API installed, and the
API can be deployed without NumPy or scikit-learn present.

## Status

- **Preprocessing (Phase 2): implemented, tested and working.** Six stages — load,
  validate, clean, featurise, target, write — producing
  `data/processed/traffic_processed.csv` with a metadata sidecar.
- **Training (Phase 3): not implemented.** No real dataset and no trained artifact
  ship with this repository, so `train`, `evaluate` and `predict` exit with a clear
  error and non-zero status rather than generating placeholder metrics.

The pipeline has only been exercised against a deterministic **simulated**
fixture. It is prefixed `SIMULATED_`, carries a provenance sidecar, and every
report banners it. It is not real-world data and results from it are meaningless
as traffic findings.

## Modules

| File | Responsibility |
| --- | --- |
| `preprocessing.py` | Data contract, loading, validation, cleaning, feature engineering, target derivation, chronological splitting, output |
| `train.py` | Estimator construction, training loop, artifact save/load, metrics |
| `evaluate.py` | Scores an artifact on a reproducible held-out split |
| `predict.py` | Inference for raw observation records |
| `data/sample/generate_simulated_dataset.py` | Regenerates the simulated fixture |

Shared constants such as `FEATURE_COLUMNS`, `TARGET_COLUMN` and
`CONGESTION_RATIO_BINS` live in `preprocessing.py` and are imported everywhere
else, so a schema change applies to training and inference simultaneously.
`predict.prepare_records()` calls the same `create_features()` used for training,
which prevents feature drift between the two.

## Workflow

```bash
pip install -r ml/requirements.txt

# Generate the simulated fixture (not real-world data).
python -m ml.data.sample.generate_simulated_dataset

# 1. Prepare a real dataset -> data/processed/traffic_processed.csv
python -m ml.preprocessing --data ml/data/raw/<dataset>.csv --write-summary

# 2-4. Phase 3; these currently exit non-zero with an actionable message.
python -m ml.train    --data ml/data/raw/<dataset>.csv
python -m ml.evaluate --data ml/data/raw/<dataset>.csv
python -m ml.predict  path/to/records.csv
```

## Dataset schema

Required columns: `timestamp`, `road_segment_id`, `avg_speed_kph`, plus either
`free_flow_speed_kph` or a pre-computed `speed_ratio`. Optional features used
when present: `flow_veh_per_hr`, `occupancy_pct`, `temperature_c`,
`precipitation_mm`, `weather_condition`, `is_incident`.

## Target and leakage

A dataset-supplied congestion label is preferred and preserved; the label mapping
is recorded so predictions can be decoded. Otherwise the target is derived from
`speed_ratio` in four bands — free flow (≥ 0.75), moderate (0.40–0.75), heavy
(0.15–0.40), severe (< 0.15). These are engineering defaults, not a published
standard, and a derived label is a convention rather than ground truth.

`avg_speed_kph`, `flow_veh_per_hr`, `occupancy_pct` and `speed_ratio` determine
the label and are therefore **excluded from the model's inputs**. Only their
history (strictly backward lags and rolling means), calendar fields, static
segment capacity, encoded identity and incident flags are used. Splitting is
chronological, because adjacent traffic observations are autocorrelated.
